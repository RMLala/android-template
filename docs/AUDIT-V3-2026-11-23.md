# Audit AppForge V3 — organisation RMLala — 23 novembre 2026

## Périmètre et méthode

Inventaire de 20 dépôts accessibles sur la branche par défaut, comparaison avec `APPFORGE-STANDARD-V3.md`, lecture des sources, workflows, PR et artefacts GitHub Actions. Ce rapport distingue les faits visibles dans le dépôt des essais qui exigent un appareil ou un compte Cloudflare de production.

Le contrôle ne modifie aucune donnée métier, licence, secret, base D1 ou objet R2. Aucun APK/HTML/EXE n'est livré à l'utilisateur dans le cadre de cet audit.

## Évolutions depuis le contrôle du 20 novembre

Quatre dépôts supplémentaires sont maintenant accessibles : `AgriMarche-MG`, `appforge-business-manager`, `appforg-ultimate-claude` et `appforge-studio-ultimate-gp`.

Évolutions notables :
- AppForge Studio : PR #43 a ajouté la lecture administrative des quotas ; le déploiement du Worker du 22 novembre a réussi. PR #44 a été fusionnée dans la branche de PR #42, pas dans `main`. PR #42 reste ouverte et porte des changements fonctionnels.
- WorshipFlow : PR #11 fusionnée ; la CI Android de `main` est verte.
- Passkeep : PR #4 fusionnée ; la CI Android de `main` est verte.
- CPV Hebdo : PR #7 documentaire fusionnée pendant ce contrôle ; CI de la PR et du push `main` réussie.
- AgriMarche, Gestion Commerce Mixte et Pilotage Financier : les copies locales du standard ont été synchronisées depuis le référentiel central par PR documentaires. Les contrôles PR étaient verts avant fusion ; après fusion, le build main d'AgriMarche est vert, mais les builds main de Gestion Commerce Mixte et Pilotage Financier échouent dans l'étape de présence des secrets de signature. Leur job Debug réussit ; les jobs Release signés sont donc ignorés. Ce défaut de secrets préexistait au contenu documentaire et bloque les APK Release.

## Écarts prouvés sur les branches principales

### AppForge Studio et Business Manager

- Le test [ultimate-business-integration.test.cjs](https://github.com/RMLala/appforg/blob/main/tests/ultimate-business-integration.test.cjs) exige explicitement `srcdoc` et l'iframe `ultimate-business-frame`. Cela contredit la règle de consolidation en navigation Studio sans iframe.
- Le module Business Manager contient encore un écran PIN autonome à 4 chiffres. Son texte précise que ce PIN ne chiffre pas la base du navigateur.
- Le module indique explicitement : « Chiffrement des exports : non disponible dans cette version ».
- Le verrou Business Manager partagé et la suppression de l'iframe ne sont pas livrés sur `main`. PR #42 reste ouverte ; PR #44 a été fusionnée dans sa branche de travail uniquement.
- Version incohérente sur `main` : l'écran À propos indique 15.8.2, tandis que `package.json`, Gradle et le générateur de build indiquent 15.8.8. La correction 15.8.14 est dans la branche PR #42, pas dans `main`.
- Le README indique que le verrouillage global biométrie/PIN est facultatif et désactivé par défaut. Le plugin natif propose biométrie forte et identifiants Android, mais pas de méthode de PIN applicatif à 4 chiffres. Le verrou Android visible et le README ne décrivent donc pas un contrat cohérent.
- Point positif : la page À propos & Support Studio comprend version/édition/date, statut Cloud, guide/FAQ, support, diagnostic avec consentement et confidentialité/mentions. Aucun historique de versions n'est inséré dans cette page.
- Le partage natif Studio utilise le sélecteur Android, sans OAuth intégré, et le code propose AES-GCM/PBKDF2 facultatif. Cela ne couvre pas l'export Business Manager, qui reste non chiffré.

### Autres applications

- **WorshipFlow** : le HTML contient un manifeste PWA et enregistre `sw.js` hors Capacitor. Les tests confirment un verrou PIN facultatif, désactivé par défaut, et un réglage biométrique séparé. La sauvegarde partagée est un JSON sérialisé sans chiffrement de sauvegarde ; le chiffrement du stockage local ne protège pas automatiquement ce fichier. La carte À propos affiche version, marque et support, mais pas le statut de licence/Cloud.
- **CPV Hebdo** : partage Drive par sélecteur Android sans OAuth et chiffrement AES-GCM optionnel. Le code et le texte de réglages disent explicitement que le verrou PIN est facultatif ; la biométrie est un réglage séparé. Le support affiche version, licence et état Cloud.
- **LifeOS** : `DriveActivity` utilise Google Identity/OAuth avec le scope `drive.appdata`. `BackupStore` chiffre la copie locale AES-GCM, mais `DriveFiles.backup` récupère la valeur déchiffrée puis l'envoie comme JSON à Drive. Le dépôt contient aussi manifeste et service worker PWA. Les PR #2 et #3 (suppression PWA/Drive natif puis Cloud V3) restent ouvertes ; ces corrections ne sont pas sur `main`.
- **Biznako** : l'écran À propos de `main` dit qu'aucun système de licence/activation n'est configuré et que les sauvegardes JSON ne sont pas chiffrées. La PR #14 d'accès Cloud par licence est ouverte, non fusionnée.
- **MadaCommerce** : README choisit Firebase/Firestore + Firebase Auth et annonce une distribution Web/PWA ; le dépôt contient manifeste, service worker et script d'enregistrement PWA. Le workflow principal produit seulement un APK Debug ; aucune intégration au Worker central n'a été trouvée dans les fichiers examinés.
- **École du Saint Esprit (`est`)** : le statut initial `isGoogleSynced` vaut `true` et `triggerAutoSync()` se contente de modifier le texte et l'heure affichés ; il ne réalise aucun appel réseau. Les dépendances Google Sign-In/Firestore sont commentées. Le workflow ne construit qu'un Debug APK et le `minSdk` est 24, pas 23. Le workflow V3 central est un contrôle de dépôt, pas une preuve d'intégration de licence.
- **AgriMarche MG** : le prototype crée son propre Worker et ses tables D1, et attend un binding privé `LICENSE_AUTHORITY` exposant `/internal/v1/cloud/verify` et `/internal/v1/cloud/authorize`. Ce contrat n'est pas celui des routes publiques du Worker central V3 ; aucun binding de production ni test Cloudflare réel n'est prouvé. Le dépôt ne contient pas de ressources d'icône Android dans l'arborescence examinée.
- **Liberté** : les tests statiques couvrent À propos/support sans historique, partage Android sans OAuth, format AES-256-GCM, absence de PWA et chemins biométrie/PIN. La PR #15 qui ajoute le Cloud pendant l'essai reste ouverte ; la synchronisation Cloud en production n'est donc pas certifiée. Le README et le package.json affichent des versions différentes.
- **Passkeep** : les tests du dépôt couvrent l'ouverture biométrique prioritaire et le PIN à 4 chiffres de secours, ainsi que la sauvegarde chiffrée. Le build main est vert. L'existence et les droits du produit `PASSKEEP` dans D1 n'ont pas été confirmés par un audit D1 en lecture seule.
- **Prompti**, **Prompti Maître** et **PâtissPro MG** : leurs PR d'initialisation restent ouvertes ; les builds CI de branches ne valent pas livraison sur `main`.
- **AppForge Business Manager** : dépôt HTML autonome séparé, sans preuve d'APK intégré à Studio.
- **AppForge Ultimate Claude** : prototype HTML local Phase 1, tests unitaires verts, sans preuve de build Android ni de Worker V3.
- **AppForge Studio Ultimate GP** : PR d'initialisation ouverte et contrôle HTML/JavaScript en échec.

## Points non vérifiables dans ce contrôle

- Qualité visuelle réelle de tous les logos, sur densités et appareils différents.
- Tests biométriques/PIN sur appareils physiques, y compris retour d'arrière-plan et changement d'appareil.
- Synchronisation D1 complète sur deux téléphones, conflits réels et restauration sans perte.
- Liste complète des produits, licences, révocations et droits Cloud de production : workflow D1 read-only non exécuté.
- Existence et fonctionnement du bucket R2, ainsi qu'un upload/download authentifié : avertissement de provisioning et absence de test réel.
- Installation et lancement de tous les APK signés sur appareils physiques.
- Livraison Drive automatique : aucune automatisation OAuth de transfert n'est activée ; seuls les partages natifs manuels prévus par les applications subsistent.

3. **Sécurité et livraison** : rendre le parcours biométrie prioritaire + PIN cohérent, chiffrer les sauvegardes exportées, corriger les applications qui utilisent OAuth/PWA ou des statuts Cloud simulés, puis valider les APK sur appareil.
